# 认证与取数路径评估 —— 「接入浏览器模块，登录然后重绘 UI」能不能做

> ## ★★ 修正（2026-10-13 当天，依据 pyicloud 官方文档核实）
>
> **本文结论二（浏览器过认证、取 token 喂协议）作废 —— 不需要浏览器。**
>
> 上一轮推荐它，是因为我当时以为「SRP-6a + GSA + 2FA 得自己写，交给浏览器最省」。
> 查证 pyicloud（timlaing fork）官方文档后发现：**这些它全都已经实现好了**，
> 而且是 `pip install` 就有的现成能力：
>
> | 我以为要自己写的 | pyicloud 现成的 |
> |---|---|
> | SRP-6a + GSA 登录 | `PyiCloudService(user, pwd)` 一行 |
> | 中国大陆账号特化 | `china_mainland=True` |
> | 2FA 取码 / 提交 | `request_2fa_code()` / `validate_2fa_code()` |
> | 免反复 2FA | `trust_session()`（Apple 记住本机，之后数周不再要码） |
> | 安全密钥 / FIDO2 | `security_key_names` / `confirm_security_key()` |
> | 旧 2SA 流程 | `trusted_devices` / `send_verification_code()` |
> | 会话保活轮询 | `refresh_interval`（默认 300 秒） |
>
> **所以 107 MB 的 WebEngine、CDP 进程管理，都不用付。** 认证改成 pyicloud 直登，
> 2FA 码在 Qt 侧弹个输入框收即可。
>
> 浏览器方案**降级为后备**：只在 pyicloud 日后被 Apple 改动打断、且来不及修时才启用。
>
> 结论一（浏览器不该当 UI）与结论三（取数走协议不抓 DOM）**不变，且更成立** ——
> 既然协议路径有现成库，抓 DOM 就更没有理由了。

**新结论：浏览器不用接，也别接。**

## 补充：官方客户端的登录凭据能不能复用（2026-10-13 实测）

**不能，也不该。** 实测本机（iCloud for Windows，UWP `AppleInc.iCloud_nzyj5cx40ttqa`）：

- Windows **凭据管理器里没有任何 Apple / iCloud 条目** —— 这条路根本不存在
- 账号 token 在 `com.apple.AOSKit.plist`，值是 **DPAPI 加密**的私有 blob
  （前缀 `01 00 00 00` + provider GUID `df9d8cd0-1501-11d1-8c7a-00c04fc297eb` = `CryptProtectData`）
- `keychain-2.db` 是**同步过来的 iCloud 钥匙串**，不是登录凭据

即便解开也**格式不对**：里面是原生 AOS token（`mmeAuthToken` / `cloudKitToken` /
各 dataclass 服务 token），而 CloudKit **Web Services** 要的是网页会话的
`X-APPLE-WEBAUTH-TOKEN` cookie 族 + DSID。

而且**收益极小**：复用最多省一次「输账号密码 + 一次 2FA」，
而 `trust_session()` 之后**数周免 2FA**。用一个无契约、随时会变的私有格式
去换一次输入 —— 不划算。

**另有第三条路成本更低**：**App 专用密码 + CalDAV**（零 2FA、口令可一键吊销、
协议公开）。代价是只对**未被升级到 CloudKit 的旧清单**有效，可能一个清单都读不到。
两条路都用只读探针 `sidecar/probe_reminders.py` 实测判定，
详见 `doc/待办/02-待办Reminders-云盘式管理.md` 的第一、二节。

## 凭据与风控契约（2026-10-13 定，实现认证前必读）

用户明确要求：**不许有毫秒级重试，不许连续尝试十次百次**。下面是核实后固化的规则，
探针与未来的 Qt 登录表单都必须遵守。

### 1. 口令不落盘、不进日志、不走命令行

- SRP-6a 的语义就是**明文口令永不出本机**：客户端只发 `sha256(口令)` 派生的证明，
  连 Apple 服务器也拿不到可用口令。pyicloud 的 `SrpPassword` 也只缓存 hash，
  **库内没有任何把口令写进日志的代码**（已逐文件核实）。
- 探针只 `print` 掩码，不写任何文件。
- **刻意不提供 `--password` / `--app-password` 命令行参数**：命令行会进
  PowerShell 历史（PSReadLine 落盘的 `ConsoleHost_history.txt`）和进程命令行
  （WMI / 任务管理器可查），等于把口令写进本机日志 —— 比不设防更糟。
  非交互场景改用环境变量，且**用完即删**。

### 2. 认证只允许单次，失败即退

| 动作 | 凭据提交次数 |
|---|---|
| 路 B CalDAV 默认 | **1 次**（只打地区探测到的那个 host） |
| 路 B `--probe-both-hosts` | 最多 2 次（仅怀疑地区判断错时） |
| 路 A pyicloud | **1 次**（一次 SRP 登录；2FA 提交也仅一次） |

Apple 的失败计数**按账号累加**，连续的失败登录正是风控锁号的触发条件。
所以：失败后**不重试、不退避、不循环**，直接退出并打印原因；
用户改对了再跑**一次**。**探针连跑本身也要克制** —— 连续重跑同样累加计数。

### 3. ⚠ 别让"自动重启"变成"自动重登"（架构级约束）

C++ 侧对旁路进程有**自动重启退避**（`SidecarClient::scheduleRestart`，1s → 2 → 4
… 30s 封顶，并且会一直重试）。当前旁路只做本地 db 采集，不碰 Apple，所以无害；
但**待办功能上线后**，如果登录逻辑放进 `serve.py` 的启动路径，就会变成：

> 进程起不来 → 退避 1s → 拉起 → 登录 → 进程又挂 → 2s → 拉起 → 登录 → …

**几秒钟一次登录尝试，正是要禁止的那件事，而且是机器自动跑出来的。**

约束：

- 认证**不得**放在会被自动重启的启动路径上。
- 需要复用时优先用**会话 token 静默请求**（带 cookie 打 API，不打认证端点）。
- token 失效 → 标记 `needsRelogin` 并**停止自动动作**，等用户手动点"重新登录"。
- 探针/表单之外的任何地方都不许出现登录调用。

### 4. 库内自动重试核实结果（确认不会在背后重试）

| 库 / 位置 | 结论 |
|---|---|
| pyicloud `_authenticate` / `_srp_authentication` | 单次 POST，无循环；失败抛 `PyiCloudFailedLoginException` |
| pyicloud `PCS_MAX_RETRIES = 10` | 仅用于**照片服务**的设备 cookie 授权轮询（带固定 sleep），与登录、待办无关 |
| pyicloud `family_poll_max_retries` | 仅用于 Find My iPhone 家庭成员轮询 |
| pyicloud CloudKit 客户端 | 遇 `THROTTLED` / `TRY_AGAIN_LATER` / `ZONE_BUSY` 是**抛 `CloudKitRateLimited`**（带 `Retry-After`），**不自动重试** |
| caldav `rate_limit_handle` | **默认关闭** —— 默认遇 429/503 直接抛异常，不 sleep 重试 |
| caldav `retry_on_failure` | 只作用于**写**请求（PUT/POST），且只重试一次；本次只读，用不到 |

### 5. 会话缓存是等价凭据

`.sessions/`（`*.session` + `*.cookiejar`）里是**登录成功后**的 `session_id` /
`auth_attributes` / `trust_token` —— 数周内可**免 2FA 直接复用**，敏感度等同口令。
- 不进版本库（venv 的 `.gitignore` 已覆盖整个 `runtime/`）。
- `--clear-sessions` 或删目录 = 退出登录。

### 6. Qt 登录表单（若走路 A）的验收标准

一次点击 = 一次提交；失败只弹提示，**不自动重试、不退避重试**；
要再试必须用户再点一次。这条写进实现，不接受"用户体验不好所以自动重试"。

## 原始评估（保留备查，其"认证交给浏览器"的建议已作废）

一句话结论：**能。而且它能把整个「认证层」删掉** —— 但方向要掰正：
**浏览器只该用来过登录，不该用来抓数据。**

## 一、这句话里的两个岔路

「接入浏览器模块，登录然后重绘 UI」= 三件独立的事，可以拆开各自选：

| 环节 | 谁来做 | 说明 |
|---|---|---|
| 登录（SRP-6a + GSA + 2FA） | **浏览器** | 交给 Apple 自己的页面，我们零代码 |
| 取数（备忘录 / 待办） | **协议**（CloudKit Web API） | 契约稳定、有文档；**不要抓 DOM** |
| 画界面 | **QML 自绘**（保持现状） | 现有监控语义、托盘、通知都还在 |

「重绘 UI」有两种理解，代价差一个数量级：

- **读法一**：浏览器只当管道，数据抓出来喂**我们自己的** QML → 推荐
- **读法二**：浏览器直接当界面，注入 CSS 把 iCloud 页面**换皮** → 等于做个 iCloud 专用浏览器，
  且 Apple 的 DOM class 是哈希的（`.note-title-8f3a`），每次发布都可能断，我们永远在追

## 四、推荐：路线 D —— 浏览器过认证，协议取数，QML 自绘

**为什么不是「浏览器全包」**：认证是这个项目里最脏最重的部分 ——
SRP-6a 握手、GSA 二次认证、2FA 弹窗、风控锁号、ADP 端到端加密降级。
这些交给 Apple 自己的登录页 = **白送**，一行都不用写。

而取数恰好相反：CloudKit Web Services 是**公开文档化**的 REST 接口，
契约比 DOM 稳得多。用 DOM 抓数据是拿最脆弱的方式去做最需要稳定的部分。

**关键接点**：浏览器登录后，我们能读到这几条 cookie / 会话值 ——

```
X-APPLE-WEBAUTH-TOKEN      （双因素会话票据，pyicloud 正是要它）
X-APPLE-DS-WEB-SESSION-TOKEN
X-APPLE-WEBAUTH-USER       （DSID）
```

拿到它们 = 拿到了 pyicloud 需要的**全部凭据**。于是
**SRP-6a + GSA + 2FA 全部不用实现**，直接进入协议取数。

> 一句话：**浏览器负责「证明你是你」，协议负责「取数据」。**

## 五、第一刀（可逆、零体积、不碰主程序）

做一个独立探针 `sidecar/probe_browser_auth.py`（不动现有一行代码）：

1. 起一个**独立 user-data-dir** 的 Edge：`--remote-debugging-port=9222`（只绑 127.0.0.1）
2. 弹出窗口 → 用户手动登录 iCloud（含 2FA）→ 登录态留在该 profile 目录
3. Python 侧用 websocket 走 CDP 读 cookie，并试调一次 CloudKit Web API 列提醒事项清单
4. 用完关掉这只看门狗进程，端口回收

**验证三件事（决定后面要不要付 107 MB）**：

| # | 待验证 | 通了说明 |
|---|---|---|
| 1 | 能否拿到 `X-APPLE-WEBAUTH-TOKEN` 系列 | 认证层彻底外包，02 的 6 条认证待办作废大半 |
| 2 | 用这些 token 能否直接调 CloudKit Web API 列出「提醒事项」清单 | **不需要内嵌 WebEngine，省 107 MB** |
| 3 | 登录态能持久多久（profile 目录复用） | 决定「多久要重登一次」的产品体验 |

**分支**：若第 2 条不通（token 不够、还需页面内 JS 会话）→ 才付 107 MB 内嵌
WebEngine，用 `runJavaScript` 取页面内的会话与数据。**先验证再掏钱，不预先打包。**

## 六、风险

| 风险 | 处置 |
|---|---|
| DOM 抓取是脆弱契约 | 只在协议路线走不通时当兜底，且把选择器集中在一个文件里 |
| 多一个外部浏览器进程要管 | 只绑 127.0.0.1、用完即关、parent 死了随 stdin/管道一并退出 |
| CDP 端口暴露 | 不监听 0.0.0.0；端口随机化；退出时确认进程已死 |
| 绿色单文件形态 | 本方案不增加打包体积；且本工具本来就依赖 iCloud 客户端 |
| ADP（高级数据保护） | 网页端也可能读不到 → 明确降级提示，不做无意义重试 |
| 风控锁号 | **用副 Apple ID 验证**，不拿主力号试 |
