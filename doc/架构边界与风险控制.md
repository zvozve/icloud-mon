# 架构边界与风险控制（QML + C++ + Python 旁路）

日期：2026-10-13 ｜ 分支 dev ｜ 配套：`doc/技术选型评估.md`

本文回答一个具体担忧：**三种语言混用会不会让程序变乱、变得容易出问题。**

结论：**语言数量本身不是风险来源，职责重叠才是。** 真正会出事的只有四条具体机制，
它们与语言数无关；而当前的分层比现状（C++ 单进程里同时做数据、判定、系统集成、界面桥接）
耦合更低。

---

## 一、三条边界（定死，不允许越界）

| 层 | 只管这件事 | 明确禁止 |
|---|---|---|
| QML（26 个文件） | UI：显示 + 用户手势 | 不碰数据、不碰 SQL、不碰文件系统、不直接与 Python 通信 |
| C++ / Qt | ① **客户端控制**：iCloud 启停（taskkill 四进程 / `explorer shell:AppsFolder\<AUMID>` 拉起）② **桌面外壳**：托盘、单实例、系统通知、定位文件、开机自启 ③ **旁路生命周期**：拉起、看护、终止 ④ **桥接**：解析 NDJSON 并分发为 QML 属性 | 不读 iCloudDrive.db、不做状态判定、不实现 Apple 协议 |
| Python 旁路 | 采集与判定：db 只读查询、活动指纹、卡死判定；将来的网页 API（备忘录/待办/照片） | 不建窗口、不做托盘、不弹通知、不写除自身配置外的任何东西（启停当前不在此侧，可按"选边原则"迁入，见下） |

一句话版本：**Python 采集、C++ 客户端控制、QML 界面。**

### 选边原则：按能力选，不按语言选（2026-10-13 用户明确）

**判据是"谁做得更好"：更准、更快、更省事、更不容易出错的那一侧胜出，不搞语言教条。**
Python 只要在某一项上更优，就把这一项放 Python，不受上表约束。

但**唯一不可破的红线是：同一件事只允许一处实现。** 判断标准如下：

| 情况 | 处理 |
|---|---|
| 一侧明显更优（更准/更快/更省事） | 放那一侧，另一侧不保留任何同类代码 |
| 两侧都能做、效果相当 | 放**已经实现且已实测过坑**的一侧（不为了分层而重写） |
| 两侧都能做、但一侧与 UI 状态耦合更紧 | 放耦合更紧的一侧，少一次 IPC 往返 |
| 需要搬迁 | **整块搬走**：搬的那次提交里删掉旧实现，不允许"先并存一阵" |

### 当前各项归属与可迁条件（实测后再定，不预设）

| 能力 | 当前归属 | 若出现下列情况则改归 | 现状判据 |
|---|---|---|---|
| 取数 + 判定（db 只读、指纹、卡死） | Python | — | 实测采样 45~96ms，与 C++ 同量级；Python 迭代更快 |
| iCloud 启停（taskkill / explorer 拉起） | C++ `IcloudService` | 需要更复杂的进程等待/退避重试/多步编排，且 Python 侧写起来明显更短时 | 两侧都是调同一个 taskkill，**效果打平**；C++ 侧已实现、两个坑（128 视为成功、AppsFolder 反斜杠）有实测记录，且能直接驱动 UI 的 busy/progress 文案，省一次 IPC → 暂留 C++ |
| 桌面外壳（托盘/单实例/通知/定位文件/自启动） | C++ | 不迁（Qt 原生 API 已就绪，换语言只增不确定性） | 无收益 |
| 界面 | QML | 见 `doc/技术选型评估.md` | 无收益 |
| 网页 API（备忘录/待办/照片） | Python（待做） | 不迁（生态只在 Python 侧） | pyicloud/icloudpd 现成 |

早期版本的本节曾写成"客户端控制**必须**归 C++"，那是把分层当教条；
正确表述是"当前归 C++，因为效果打平而它已经跑通"，随时可按上表改判。

因此 `sidecar/` 里暂时**没有** service.py；主程序若误发 `icloud` 命令，
旁路会明确回错误（而不是静默忽略），防止将来误以为两边都支持控制。

通信是**单向**的：QML → C++ → Python（命令），Python → C++ → QML（JSON 事件）。
**不允许反向调用**（Python 不直接驱动 UI，QML 不直接读 Python）。

为什么这样就"不乱"：三者职责互斥且单向依赖，任何一次数据异常都能定位到唯一一层，
不存在"C++ 读了一遍、Python 又读了一遍、两边数字不一样"的局面。

## 二、四条真风险与对应措施

### 1. 双真相源并存（最容易把项目搞臭的）

迁移期若 C++ 数据源与 Python 旁路同时活着，界面数字可能来自任意一边，
届时出现的差异无法归因。

措施：
- **一次性切换**。切换提交里就删掉旧调用路径（`IcloudMonitor` / `IcloudService` 不再被 Bridge 引用），
  不允许"先并行跑一阵看看"这种长期双跑。
- 双轨比对是**一次性的验证动作**（同一时刻两边数值对照一遍），不是长期运行态。

### 2. 旁路进程生命周期

拉起失败、中途崩溃、僵尸残留 —— 都会表现为"界面数字冻结"，
而冻结和"已同步"在视觉上无法区分。

措施：
- 父子绑定：主程序退出时终止旁路（`QProcess` 终止 + 等待）；父进程崩溃时旁路通过
  stdin EOF 自行退出（`serve.py` 已是阻塞读 stdin，EOF 即退出）。
- 心跳：主程序定期 `{"cmd":"ping"}`，超时（如 3 个采样周期）判定离线。
- 拉起失败回退：`ready` 事件未在超时内到达 → 进入离线态，重试有退避，不无限刷。

### 3. 失败必须可见（最容易被忽略）

旁路挂了之后，界面若继续显示上一次的"已同步"，用户会以为一切正常 ——
这与本工具的立身之本（让人发现 iCloud 卡住）直接冲突。

措施：
- 新增离线态，**离线时不沿用旧数据**：状态区显示"监控不可用（旁路离线）"，
  数字置灰或显示 "—"，绝不用旧值假装正常。
- 异常口径与现状一致：`dbOk=false` / 卡死 / 故障 / 超配额 / 错误码，
  现有 `stateName`、`anomalies` 语义不变（旁路已按此对齐）。

### 4. 打包与跨进程调试

两个可执行体 + 内嵌 Python 运行时，任何一处路径/权限问题都会变成"启动即失败"。

措施：
- 路径一律从环境变量/注册表取，不写死用户名（现状已遵守）；
- 日志落同一目录、统一时间戳格式、旁路日志带 pid，便于跨进程对齐；
- NDJSON 协议带版本字段，主程序遇到不认识的版本直接报错而非猜；
- 打包后必须跑冒烟：单文件 exe → 拉起旁路 → 收到 `ready` → 收到 ≥1 帧 `snapshot`。

## 三、为什么不把三种东西塞进一个进程

反面做法是在 C++ 里用 pybind11 内嵌 CPython 解释器（单一进程、调用最直接），
但它把四条风险全部放大：

| 内嵌解释器的问题 | 独立进程为何更稳 |
|---|---|
| Python 侧异常/崩溃直接带走整个 GUI 进程 | 旁路崩溃只表现为"离线"，主程序照常运行、能提示 |
| GIL 与主线程/渲染线程交互，卡顿难复现 | 采样在另一个进程，完全不占 UI 线程 |
| Python DLL 与 Qt DLL 同进程加载，版本/CRT 冲突难查 | 两套运行时天然隔离 |
| 调试时无法单独重启 Python 侧 | 旁路可单独 kill、单独重启、单独用 probe.py 复现 |

代价是多一层 IPC（NDJSON，约 200 行代码）和一个进程。这个代价是明确、可测的。

## 四、这套安排的验收标准

改造完成后，若以下都能成立，则"三语言 = 乱"这个担忧不成立：

1. 连续运行 8 小时，无僵尸进程、无句柄泄漏（任务管理器核对进程数与句柄趋势）；
2. 手动 kill 旁路进程 → 界面 3 个采样周期内进入离线态，且不再显示任何数字；
3. 重启旁路 → 界面自动恢复，无需重启主程序；
4. 主程序退出 → 旁路进程随之消失（无残留）；
5. 单文件 exe 在干净机器上冒烟通过（无 Python 环境）。

---

## 五、边界（不做的事）

- 不做长期双轨并行运行（见 2.1）。
- 不让 Python 侧接触任何 UI/托盘/通知 API（保持可无界面运行，便于测试）。
- 不在 Python 侧实现任何"绕过 Apple 认证"的行为；凭据仅用于本机读取自己的数据。
