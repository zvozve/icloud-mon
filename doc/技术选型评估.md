# 技术选型评估：界面框架与数据层语言

日期：2026-10-13 ｜ 分支 dev ｜ 结论：**界面维持 Qt/QML，数据层迁 Python 旁路（已落地），不转 Electron**

> 复盘一句：这份评估本该在写 `sidecar/` 之前出。侧车那部分代码在任何一个方案下都能复用
> （数据层语言与界面框架正交），所以不算沉没成本，但流程上记一条：
> **凡涉及框架级改动，先出评估、后动手。**

---

## 一、先量清楚"当前功能"到底有多少

评估收益必须对着实际功能清单，不能对着"一个桌面程序"这种模糊对象。

| 层 | 具体内容 | 代码规模 | 是否与界面框架绑定 |
|---|---|---|---|
| 数据读取 | iCloudDrive.db 只读查询（14 条 SQL）、另外 3 个 SQLite 库（相册/密码/书签） | IcloudMonitor 907 行 + IcloudCategories 447 行 | 否 |
| 进程探测 | Toolhelp32 单次快照枚举 4 个 iCloud 进程 | IcloudService 部分 | 否（但需原生 API） |
| 卡死判定 | 活动指纹 + 历史 jsonl + 停滞秒数 | IcloudMonitor 部分 | 否 |
| 系统集成 | 托盘图标 + 右键菜单 + 双击唤起、单实例互斥、开机自启（注册表 Run）、Windows 系统通知、explorer /select 定位文件、打开 URL | main.cpp 723 行 | **是（框架 API）** |
| iCloud 控制 | taskkill 四进程、`explorer shell:AppsFolder\<AUMID>` 启动 | IcloudService 182 行 | 否 |
| 界面 | 首页/分类页/Drive 页/设置页 + 侧边栏拖拽排序 + 主题 + Toast | ui/ 26 个 QML 文件 | **是** |
| 分发 | windeployqt → Enigma Virtual Box 单文件 exe，27.2 MB，绿色免安装、免管理员 | packaging/ | **是（打包方式）** |
| 现有约束 | 构建为 **msvc2019 32 位**；常驻托盘；无管理员权限；无 Qt TLS（改用 WinHTTP） | — | — |

关键点：**只有"系统集成 + 界面 + 分发"这三块与框架绑定，"取数 + 判定"这一大块（约占逻辑量的一半）与框架完全无关。**

## 二、三个候选方案

| | A 现状 Qt/QML + C++ | B Qt/QML + C++ 壳 + **Python 数据层旁路**（当前 dev 分支已落地） | C **Electron + Python**（+ C++/原生模块，必要的话） |
|---|---|---|---|
| 界面 | QML 26 文件（保留） | QML 26 文件（保留） | 全部重写为 HTML/CSS/JS |
| 数据层 | C++ | Python 旁路进程 | Python |
| 系统集成 | Qt/C++ | Qt/C++（保留） | Node/Electron API（部分需原生模块） |
| 通信 | 直接函数调用 | NDJSON over stdin/stdout | IPC（同样要跨进程） |

补充说明方案 C 的"必要的话 +C++"：托盘、单实例、Toolhelp32 这类在 Electron 里有现成 Node API
或第三方包，真要 C++ 通常是编 native addon 或保留一个侧车 exe —— **注意：这与方案 B 的
"Python 侧车"在架构上同构**，Electron 并没有省掉跨进程这一层，只是把 UI 换了语言。

## 三、逐维度对比（量化）

| 维度 | A 现状 | B 侧车（已落地） | C Electron+Py | 说明 |
|---|---|---|---|---|
| 常驻内存（空闲） | 20~60 MB | 20~60 MB + 旁路约 15~25 MB | **150~300 MB** | Electron 是多进程 Chromium；社区实测"还没写业务代码常驻就近 300MB" |
| 安装包体积 | 27.2 MB | 约 27 + 25~40 MB（内嵌 Python 运行时） | **80 MB 起**（未压缩基线） | 常驻托盘小工具，用户对体积敏感 |
| 冷启动 | 0.3~0.8 s | 同 A（旁路并行拉起，不阻塞首帧） | 1~3 s | Electron 要起 Chromium |
| 采样耗时 | <100 ms（日志阈值内） | **实测 45~96 ms**（含复制 16MB 三件套） | 同 B | 数据层换语言没有性能损失，已实测 |
| **32 位支持** | ✅ msvc2019 32 位（**现状而非需求**，见第七节） | ✅ Python 有 32/64 位运行时 | Electron 43 是最后一个提供 win32-ia32 的版本，v44 起只发 64 位（**仅在"必须支持 32 位"时才成立**） | 当前 32 位构建很可能只是"手上是 msvc2019 32 位 kit"，迁 64 位对 Qt 与 Electron 都是零成本 |
| 托盘 / 右键菜单 | Qt 原生 | Qt 原生 | Electron Tray 可用（但 Linux 下限制多） | 打平 |
| 单实例 | QSharedMemory/互斥 | 同 A | requestSingleInstanceLock | 打平 |
| 系统通知 | QSystemTrayIcon 已实现 | 同 A | Electron Notification（**macOS 需签名才显示**；Windows 无此限制） | 打平（Windows） |
| 定位文件 / 打开 URL | QDesktopServices / explorer /select | 同 A | shell.showItemInFolder / openExternal | 打平 |
| 开机自启（免管理员） | 注册表 Run | 同 A | app.setLoginItemSettings 或写注册表 | 打平 |
| 单文件绿色分发 | Enigma VB 已验证 | 同 A | 无等价物：asar + 便携版可做，但体积大、解压慢、杀软误报显著更高 | **B 明显优** |
| 免管理员 / 免运行库 | ✅ | ✅（内嵌运行时） | ✅ | 打平 |
| 杀软误报 | 现版本已验证可用 | 略升（内嵌 Python 可能被启发式标记） | 明显更高（未签名 Chromium 壳 + 打包器） | A/B 优 |
| 前端开发效率 | QML 一般 | 同 A | **优**（Web 生态、组件库丰富） | C 优，但本项目 UI 简单 |
| 未来网页 API 能力 | 需自研 SRP/GSA/2FA（成本高） | **pyicloud/icloudpd 现成** | 同 B（Python），Node 侧也有库但生态薄 | B = C，都优 |
| Wine/老机器兼容 | ✅ 32 位可跑 | ✅ | ❌ 64 位 Chromium 要求高 | A/B 优 |
| 构建链复杂度 | Qt + windeployqt + EVB | 加一条 Python 打包链 | npm 工具链 + 打包器 + Python 链（**三套**） | A/B 优 |
| 协议变更时改动面 | 重编译重打包 | 改脚本，主程序不动 | 同 B | B = C |
| 跨平台（未来 Mac/Linux） | QML 可移植，系统集成需重写 | 同 A | **优**（UI 一致） | C 优，但当前无此需求 |

## 四、结论

**收益侧**：Electron 对本项目的真实增益只有两条 —— 前端开发效率、未来跨平台 UI 一致性。
本项目是"只读监控 + 托盘常驻"的工具，界面只有 4 个页面、无富文本/图表/复杂交互，
这两条增益**在当前需求下几乎用不到**。

**损失侧**（按严重度排序）：

1. ~~**32 位断供**~~ → **已作废**：32 位是现状不是需求，Electron 直接上 64 位即可，见第七节。
2. **常驻内存 5~10 倍**：20~60MB → 150~300MB。对一个"帮助人发现 iCloud 卡住"的工具，自身变成资源大户是自相矛盾的。
3. **包体 3~5 倍**：27MB → 80MB+，且失去 Enigma VB 这种单文件绿色分发的等价物。
4. **杀软误报与签名压力**上升，直接损害"双击即用"的下降体验。
5. **构建链从 2 套变 3 套**（npm + 打包器 + Python），维护成本上升。

**更本质的一点**：用户想要的能力（备忘录/待办/便签/照片，走 iCloud 网页后端）是**数据层语言问题**，
和界面框架无关。换 Electron 一行这类能力也拿不到，因为瓶颈在认证与协议（Python 生态现成），
不在 UI。所以正确的解耦是 **UI 保持 Qt/QML、数据层换 Python**，而不是把整个 UI 换掉。

**推荐：B（当前 dev 分支的路线）**，但注意这个结论依赖"目标是轻量常驻的绿色单文件工具"。
目标变了结论就变，见第七节。具体分工见下表。

### 语言分层（C++ vs Python 的收益边界）

| 层 | 用什么 | 理由 |
|---|---|---|
| 取数 + 判定 + 网页 API | **Python** | sqlite3/文件/注册表/HTTP 都是标准库或生态强项；pyicloud/icloudpd 现成；Apple 改端点只改脚本 |
| 系统集成（托盘/单实例/通知/进程枚举/定位文件） | **C++ (Qt)** | 已是原生 API，Toolhelp32 单次快照 1ms；无运行时依赖；这部分换语言只增加不确定性 |
| 界面 | **QML**（保留） | 4 个页面，已有主题/组件；重写没有收益 |
| 未来若需要联网 | **C++ WinHTTP** | 本机 Qt 无 TLS DLL（已知问题），WinHTTP 零依赖 |
| 何时才考虑 C++ 写数据层 | 采样超过 200ms 或需要实时流式 | 当前实测 45~96ms，**远未触及** |

## 五、触发重新评估的条件

出现以下任一条时，重开这份评估（否则不再讨论换界面框架）：

1. 目标平台明确放弃 32 位，且需要同一套 UI 同时上 Windows/macOS/Linux；
2. 界面复杂度跃升到需要图表 / 富文本编辑器 / 复杂表格这类 Web 生态优势明显的场景；
3. 需要多人协作开发 UI，且团队是前端背景；
4. 单文件绿色分发不再是硬需求（比如改为商店分发）。

## 六、万一要转 Electron：工作量与复用清单（备查）

| 部分 | 处理 |
|---|---|
| Python 数据层（sidecar/） | **100% 复用**，只把 NDJSON 通道接到 Electron 主进程 |
| QML 26 个文件 | 全部重写（HTML/CSS/JS），含主题、Toast、侧边栏拖拽 |
| C++ 系统集成 | 托盘/通知/单实例改用 Electron API；Toolhelp32、WinHTTP 若保留需 native addon 或侧车 exe |
| 打包 | Electron 打包器（体积/误报/签名三项都要重新验证） |
| 32 位目标 | 需在 2027-01 前决定是否放弃 |

估算：这不是"小改"，是把已验证可用、体积 27MB 的工具改造成 80MB+ 且失去单文件绿色分发的形态。

## 七、关于 32 位的反驳与论据重排序（2026-10-13 追加）

**用户指出：Electron 直接上 64 位就行，个人电脑基本没有 32 位了。**

这条成立，本文第四节原本把"32 位断供"列为第一损失是错的 —— 它把**现状**当成了**需求**。

修正后的判断：

1. 本项目用 32 位构建，很可能只是因为手上装的是 `Qt 5.15.2 msvc2019`（32 位 kit），不是硬需求。
   **若是这样，这条论据整体作废**，与是否转 Electron 无关。
2. 顺带澄清一个反向事实：**现有 Qt 版迁到 64 位同样零成本** —— 换 `msvc2019_64` kit 重新
   windeployqt + 打包即可，Enigma Virtual Box 也支持 x64。所以"64 位"不是 Electron 的加分项，
   两边都能做。
3. 因此剩下的论据只有**四条**（内存 / 体积 / 分发形态 / 构建链），这三条都属于"代价大小"问题，
   不是"能不能做"的问题。

### 论据随目标重排序

| 目标（先明确要哪个） | 结论 | 决定性论据 |
|---|---|---|
| 轻量常驻 + 绿色单文件（现状形态） | 保持 Qt/QML + Python 旁路 | 内存 5~10 倍、体积 3~5 倍、失去 EVB 等价物 |
| 更好的 UI 开发体验 / 未来跨平台统一 UI | **Electron 可行**，代价是 80MB+ 包与 150~300MB 常驻 | 只要接受代价，没有技术阻碍 |
| 想要的是"能读备忘录/待办/照片" | 与 UI 框架**无关** | 瓶颈在认证与协议（Python 生态现成），UI 换栈一样要做 pyicloud 那套 |

### 与当前工作顺序的关系（重要）

不管 UI 最终选谁，**Python 数据层都必须先做**，且 100% 可复用：

```
先做:  Python 旁路数据层（已落地）  ← 两个方案共用
后定:  UI 是否换栈 —— 此时才有比较意义（数据层已就绪，换 UI 只是换壳）
```

也就是说：UI 选型**不阻塞**当前工作，可以等数据层跑通、真用起来之后再决定。
唯一需要现在确认的是：**本项目到底有没有 32 位需求**（影响是否能顺手把 Qt 版也迁 64 位）。
